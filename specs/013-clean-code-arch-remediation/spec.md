# Feature Specification: Clean-Code Signature Audit & Critical Architecture Remediation

**Feature Branch**: `013-clean-code-arch-remediation` (work carried on `feature/ado-agentic-ai`)

**Created**: 2026-09-07

**Status**: Implemented (2026-09-13, register merge completed 2026-09-22) — one high gap (GAP-069) remains `deferred`, pending an operator decision about where a DynamoDB deployment's audit database should live; every other critical or high gap in the register, including the three FR-024 contract items (GAP-019, GAP-024, GAP-054) and GAP-031 (resolved without a contract change, all four previously left open pending the same batch of operator decisions), is `remediated`

**Input**: User description: "Go through each part of the source code and identify all functions, invoke the ponytail skill and update all function signatures with clean code best practices. Go through the overall architecture, and identify and remediate all critical architecture gaps for this repository."

## Context

The platform spans a Python package and two HTTP services (measured 2026-09-07: 1,549 function definitions across 195 files, an upper bound because that walk counted nested definitions this feature does not inventory separately) and a web console (~340 definitions in 73 files, 227 exported). Function signatures have accumulated inconsistencies over twelve prior specs: positional-argument sprawl, boolean flag parameters, untyped or loosely typed parameters, missing or stale docstrings, and names that no longer describe behaviour. The constitution (Principles I, II, IV) requires readable code, documented functions, and intuitive naming — this feature brings the existing codebase into compliance rather than only applying the rules to new code.

Separately, the architecture has grown by accretion (CLI → API → agent → UI). No single review has checked the whole system against the constitution's safeguard principle (V) and migration-appropriate patterns. This feature performs that review, classifies gaps by severity, and remediates every gap classified **critical** or **high**.

"Ponytail" is the house discipline for this work: prefer deletion over addition, reuse over reinvention, stdlib over new dependencies, smallest diff that satisfies the requirement. It governs *how* signatures are cleaned — no new abstraction layers, no speculative parameters, no helper types unless three or more call sites need them.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Function Inventory & Signature Audit (Priority: P1)

A maintainer (or an LLM agent working the codebase) needs an authoritative list of every function in the repository, each tagged with the signature-quality problems it has, so that cleanup is systematic rather than ad hoc and progress is measurable.

**Why this priority**: Nothing else in this feature can be scoped, sequenced, or verified without the inventory. It is also independently valuable: a maintainer can use it to plan work even if no signature is ever changed.

**Independent Test**: Generate the inventory for the repository; spot-check 30 randomly chosen functions and confirm each is listed with the correct location and that every flagged problem is real. Confirm that the count of listed functions matches an independent count within 2%.

**Acceptance Scenarios**:

1. **Given** the repository at the feature's starting commit, **When** the inventory is produced, **Then** every function, method, and coroutine in the Python packages, services, and web console is listed with its location, its current signature, and zero or more problem tags.
2. **Given** a function with a boolean parameter that switches between two behaviours, **When** it appears in the inventory, **Then** it carries the "boolean flag parameter" tag.
3. **Given** a function with more than five parameters (receiver excluded), or with parameters lacking type annotations, or with no docstring, **When** it appears in the inventory, **Then** it carries the corresponding tag(s).
4. **Given** the inventory, **When** a maintainer filters to functions with zero problem tags, **Then** those functions are excluded from the cleanup work list.
5. **Given** the inventory was generated earlier, **When** it is regenerated after some cleanup, **Then** the tag counts reflect the current code and the previous run's counts are still available for comparison.
6. **Given** a function the generator suspects has a stale docstring or a non-descriptive name, **When** the inventory is produced, **Then** the suspicion is listed as a pending judgment-tag proposal, and once the review agent confirms or rejects it the decision is stored and reused by every later regeneration until that function's signature or docstring changes.

### User Story 2 - Signature Cleanup Without Behaviour Change (Priority: P1)

A maintainer applies clean-code signature rules to every flagged function so that any reader — human or agent — can understand what a function takes and returns from its signature and docstring alone, with zero change to observable behaviour.

**Why this priority**: This is the primary deliverable the user asked for. It directly satisfies constitution Principles I, II, and IV for the existing codebase.

**Independent Test**: After cleanup, the full automated test suite passes; every CLI command, HTTP route, and environment variable behaves identically (contract tests unchanged and green); the web console's type-check, lint, and tests pass; re-running the inventory shows zero remaining problem tags outside the documented exception list.

**Acceptance Scenarios**:

1. **Given** a function flagged with any problem tag, **When** cleanup is complete, **Then** the function has a descriptive verb-noun name, every parameter is typed, parameters number five or fewer excluding the receiver (or the excess are grouped into an existing domain object), boolean-flag parameters are replaced by two intent-named functions (or, where a split would duplicate a body of more than ten statements, by an existing enumeration or option object — or by one shared enumeration when the same flag recurs in three or more signatures), and a docstring describes purpose, parameters, return value, and raised errors.
2. **Given** a function whose signature changes, **When** cleanup is complete, **Then** every caller in the repository — production, test, web console, agent prompts, and evaluation fixtures — is updated and no call site is left referencing the old signature.
3. **Given** a public contract (CLI flag, HTTP route path or payload shape, environment variable name, persisted state schema), **When** cleanup is complete, **Then** the contract is unchanged; only internal signatures move.
4. **Given** a function that is unused anywhere in the repository and not on the protected entry-point list, **When** cleanup reaches it, **Then** it is deleted (not cleaned), its exclusively-owned tests are deleted with it, and the deletion is recorded in the structural changelog.
5. **Given** a function that cannot be brought into compliance without a behaviour change, **When** cleanup reaches it, **Then** it is listed in an exception register with the reason and the follow-up owner, and it retains a docstring explaining the constraint.
6. **Given** the cleanup is complete, **When** a reviewer inspects the diff, **Then** no new abstraction, dependency, or configuration surface has been introduced solely to support the cleanup.
7. **Given** a package's cleanup increment is finished, **When** the automated checks run on that increment alone, **Then** they pass before the next package's increment begins.
8. **Given** a module or folder whose name does not describe its responsibility, **When** cleanup reaches it, **Then** it is renamed or moved to a descriptive location, every import and document reference follows in the same change, and the move is recorded in the structural changelog.

### User Story 3 - Architecture Gap Assessment (Priority: P2)

An architect reviews the whole system — CLI, accelerator service, agent service, web console, state persistence, auth, and their integration seams — against the constitution and against migration-tool best practice, producing a gap register with severity ratings and rationale.

**Why this priority**: The register is the decision artefact for remediation. It is valuable on its own (roadmap input, risk disclosure to stakeholders) and must exist before any gap is fixed.

**Independent Test**: A separate review agent, given only the register and the constitution, reproduces each critical and high rating from the stated evidence; any rating it cannot reproduce is surfaced to the operator as a dispute.

**Acceptance Scenarios**:

1. **Given** the current architecture, **When** the assessment runs, **Then** every gap is recorded with: the component(s) affected, the constitution principle or migration-safety property it violates, concrete evidence (location or reproduction steps), severity (critical / high / medium / low), and the blast radius if left unaddressed.
2. **Given** a gap, **When** it is rated critical, **Then** it meets at least one of these tests: (a) allows a destructive or irreversible migration action without the confirmation, dry-run, or audit trail required by the constitution; (b) can expose a secret in a log, report, message, or persisted artefact; (c) can lose or corrupt migration state such that a run cannot be resumed or its outcome cannot be verified; (d) an in-code failure path (swallowed error, missing checkpoint, absent resume path) leaves no fail-safe default; (e) leaves two components disagreeing on a shared contract in a way that silently produces wrong results. Deployment topology (single database instance, single service process) does not qualify under (d).
3. **Given** a gap that meets no critical test, **When** it is rated high, **Then** it either violates a constitution principle or a migration-safety property in the default configuration, or meets a critical test only in a non-default configuration or deployment topology. Medium is reserved for readability, naming, or documentation drift with no safety impact; low is cosmetic.
4. **Given** the register, **When** a stakeholder reads the summary, **Then** the count of gaps per severity and the list of critical and high gaps with one-line descriptions are visible on the first page.
5. **Given** the assessment, **When** it covers the state persistence layer, **Then** it explicitly checks that every deployment mode (local, production, serverless job store) provides the same auditability, resume, and idempotency guarantees, and records any divergence.
6. **Given** the assessment, **When** it covers the agent service, **Then** it explicitly checks that every path to live (non-dry-run) execution passes through the human-approval and guardrail layers, and records any bypass.
7. **Given** the register is complete, **When** the review agent disputes a rating, **Then** the dispute (rating, evidence, the reviewer's alternative) is presented to the operator, and remediation of that gap does not start until the operator decides.

### User Story 4 - Critical & High Gap Remediation (Priority: P2)

A maintainer closes every gap rated critical or high in the register, with a regression check for each so the gap cannot silently reopen.

**Why this priority**: The user asked for remediation, not only identification. Critical gaps by definition threaten migration safety in regulated environments; high gaps are constitution violations that would otherwise become the next feature's criticals.

**Independent Test**: For each critical or high gap, the reproduction steps recorded in the register no longer reproduce the gap, and an automated check exists that fails if the gap is reintroduced.

**Acceptance Scenarios**:

1. **Given** a critical or high gap, **When** remediation is complete, **Then** the register entry is updated with the resolution, the location of the regression check, and the date closed.
2. **Given** a gap whose fix would change a public contract, **When** the implementation plan is written, **Then** the change and its migration note for existing deployments are listed in the plan, and the fix is applied only after the plan is approved.
3. **Given** a gap in the safeguard layer (confirmation, dry-run, audit, secret masking), **When** remediated, **Then** the fix is placed at the shared choke point through which every affected caller routes, not patched per caller.
4. **Given** all critical and high gaps are closed, **When** the full test suite, lint, and type checks run, **Then** they pass and the coverage threshold is maintained or improved.
5. **Given** medium and low gaps, **When** this feature completes, **Then** they remain in the register with a recommended follow-up, and are explicitly out of scope for remediation here.
6. **Given** a gap rated high, **When** remediation begins, **Then** signature cleanup is already complete, the fix lands on already-cleaned signatures, and no remediated function is later touched by cleanup.
7. **Given** a gap rated critical, **When** the review agent confirms the rating, **Then** remediation starts immediately regardless of cleanup progress, and the affected functions are cleaned afterwards without reopening the gap — the gap's regression check MUST still pass once their signatures change.

### User Story 5 - Documentation & Guard Rails Stay Truthful (Priority: P3)

A maintainer finds that the architecture document, the AI-assistant guidance file, the README, the rest of the documentation directory, the structural changelog, and the orphan-module guard all reflect the post-cleanup, post-remediation state.

**Why this priority**: Stale documentation is the main way that clean-up work decays. The constitution requires documentation as a first-class deliverable, but this story depends on the others completing first.

**Independent Test**: Every module path, function name, and endpoint referenced in the architecture document, the assistant guidance, the README, and the documentation directory resolves to an existing artefact; the structural changelog lists every file moved or deleted by this feature; the orphan-module guard passes.

**Acceptance Scenarios**:

1. **Given** a function or module renamed, moved, or deleted by this feature, **When** documentation is checked, **Then** no document references the old name or path.
2. **Given** a remediated gap, **When** the architecture document is read, **Then** the corrected design is described and the gap is not described as current behaviour.
3. **Given** the feature is complete, **When** the structural changelog is read, **Then** every move and deletion performed here is recorded as an append-only entry.

### Edge Cases

- A function's signature is part of a persisted or serialised contract (checkpoint payload, session record, job-store row): the signature MUST NOT change shape; document as an exception if it violates a rule.
- A function is invoked dynamically (by name string, plugin registry, or framework callback): renaming it MUST update the dynamic reference and the orphan-module allowlist. Such functions are on the protected entry-point list and are never auto-deleted.
- A function is overridden or implemented across several classes (interface / abstract method): the signature MUST change consistently across all implementations in the same change.
- A boolean flag parameter is exposed as a CLI flag or HTTP query parameter: the external flag stays; only the internal signature is restructured.
- An agent tool function's signature changes: the tool schema the LLM sees changes with it, so the role prompt, evaluation fixtures, and tool documentation that reference the old name or parameters are updated in the same change, and the agent evaluation suite passes.
- A type annotation added by cleanup must remain valid on the minimum supported Python version declared in the project's packaging metadata; cleanup MUST NOT raise that minimum.
- A generated or vendored file (migration scripts, transformer mapping tables, third-party stubs): out of scope for signature cleanup. Excluded paths MUST be listed in a checked-in exclusion file that the inventory generator reads, so the exclusion is visible, reviewable, and applied identically at every regeneration; excluded functions are reported separately in the summary and are not counted against the zero-tag target.
- The inventory count changes mid-feature because other branches merge: the inventory is regenerated at the end and the success criteria are measured against the final regeneration, so functions that arrived after the baseline are in scope for the zero-tag target exactly like the originals.
- A cleanup increment ends red and cannot be made green within three fix-and-verify attempts: the increment is reverted to the last green state, the function or module that caused the failure is moved to the exception register or split out into its own smaller increment, and the retried increment must pass before the next package begins.
- Two gaps rated critical conflict in their remediation (fixing one weakens the other): escalate to the operator with both options before applying either.
- A critical or high gap cannot be remediated without an external dependency or infrastructure change (new service, new credential store): record as deferred with the blocking dependency named, and add a compensating control that is in scope.
- A module move changes an import path that a deployment script, container image, or process entry point references by string: those references are updated in the same change and the change is called out in the migration note.
- The review agent disputes a rating and the operator does not respond: the gap is treated at the higher of the two proposed severities and remediation of it is deferred until the operator decides.

## Requirements *(mandatory)*

### Constitution Alignment *(mandatory for migration-execution features)*

This feature touches migration run, cleanup, rollback, and gate override code paths through signature cleanup and gap remediation:

- **CA-001**: Every dry-run or preview path that exists at the start MUST still exist and behave identically at the end; remediation MUST add a preview path to any critical or high gap that lacks one.
- **CA-002**: Every confirmation or documented-override path MUST be preserved; remediation MUST NOT reduce the set of actions requiring confirmation.
- **CA-003**: Signature cleanup MUST NOT cause a secret value to appear in a docstring, default value, log line, or test fixture; secret-masking choke points are in scope for the gap assessment.
- **CA-004**: Every state change that was auditable at the start MUST remain auditable; remediation MUST add audit coverage to any critical or high gap that lacks it.

### Functional Requirements

**Inventory & audit**

- **FR-001**: The maintainer's process MUST produce a function inventory covering every function, method, and coroutine in the Python package, both services, and the web console, each with location, current signature, and problem tags. The inventory MUST be a machine-readable file stored in the feature directory.
- **FR-001a**: One inventory entry is one named module-level or class-level function, method, or coroutine, or one named exported web console function, hook, or component. Nested functions, lambdas, and inline callbacks MUST NOT receive their own entries; a problem inside one MUST be attributed to the enclosing entry. This definition MUST be applied identically at every regeneration.
- **FR-002**: The inventory MUST apply these problem tags: missing docstring (for the web console: missing documentation comment on an exported function or component); stale docstring (parameters described do not match signature); untyped parameter or return; more than five parameters excluding the receiver (`self`/`cls`), with variadic and keyword-only parameters counting one each; boolean flag parameter selecting behaviour; name that does not describe behaviour (non-verb function name, or name contradicting what the body does); mutable default argument; parameter accepted but unused; return type varies by branch without documentation.
- **FR-002a**: Tags MUST be split into two classes. **Mechanical tags** — missing docstring/documentation comment, untyped parameter or return, more than five parameters, mutable default argument, parameter accepted but unused — MUST be decided deterministically by the inventory generator with no human judgement. **Judgment tags** — stale docstring, boolean flag parameter selecting behaviour, name that does not describe behaviour, return type varies by branch without documentation — MUST be proposed by the generator and confirmed, or rejected, by the review agent.
- **FR-002b**: Proposed judgment tags MUST be decided by the same separate review agent that re-derives gap ratings, never by the generator that proposed them; a proposal the review agent cannot decide from the code, or whose resolution would require a behaviour change, MUST be escalated to the operator. Every decision MUST be recorded with its rationale in a decisions file stored in the feature directory alongside the inventory, keyed so the decision survives regeneration. Later regenerations MUST reuse a recorded decision rather than re-asking, and MUST re-propose a judgment tag only when the function's signature or docstring has changed since the decision was recorded. Unconfirmed proposals MUST be visible as pending and MUST NOT count as tagged or as clean until decided.
- **FR-003**: The inventory MUST identify functions with zero references anywhere in the repository (production, tests, dynamic registries, prompts, fixtures) as deletion candidates, and MUST exclude from candidacy every function on the protected entry-point list.
- **FR-003a**: A function qualifies as a deletion candidate only when both hold: it has no static caller, and its name does not appear as a string anywhere in the repository — prompts, evaluation fixtures, configuration, documentation, CI workflows, and container definitions included. A name found by either check MUST be treated as referenced and cleaned rather than deleted.
- **FR-003b**: Generated, vendored, and data-table files MUST be excluded from the inventory through a checked-in exclusion file that the generator reads. The summary MUST report how many definitions each excluded path holds, so the exclusion is auditable and cannot silently shrink the zero-tag denominator.
- **FR-004**: The inventory MUST be regenerated by a script kept in the feature directory, so that progress can be re-measured at any point, and each regeneration MUST preserve the previous run's summary counts for comparison. Regeneration MUST be deterministic: given the same code and the same decisions file, two runs MUST produce the same tags.

**Signature cleanup**

- **FR-005**: Every function with one or more problem tags MUST be cleaned so that it has zero tags, or MUST appear in the exception register with a reason.
- **FR-005a**: If exception-register entries would exceed 2% of the total function count, cleanup of the rule driving the excess MUST stop and the situation MUST be escalated to the operator, who decides whether to raise the cap, amend the rule, or accept the behaviour change. Entries MUST NOT be added past the cap without that decision.
- **FR-006**: Cleanup MUST NOT change any externally observable contract: CLI command names and flags, HTTP route paths and payload shapes, environment variable names, persisted schema shapes, and the shapes of messages exchanged between services. This list is exhaustive. Agent tool signatures (the schema exposed to the LLM) and the package's importable Python API — module paths and public function names — are internal and MAY change.
- **FR-006a**: Functions and modules renamed or deleted by cleanup MUST be removed outright, satisfying Principle III by removal rather than by deprecation. No compatibility alias, re-export shim, or deprecation warning MAY be introduced; the structural changelog entry is the required record.
- **FR-007**: Cleanup MUST update every caller of a changed signature within the same change, including tests, the web console, agent role prompts, evaluation fixtures, and tool documentation.
- **FR-008**: Cleanup MUST NOT introduce new dependencies, new abstraction layers, new runtime configuration keys (environment variables or settings read by the product), or helper types used by fewer than three call sites. Linter, type-checker, and coverage configuration used only as guards are not configuration keys under this rule.
- **FR-009**: Functions with zero references MUST be deleted automatically rather than cleaned, together with any tests that exclusively exercised them, unless they are on the protected entry-point list. Each deletion MUST be recorded in the structural changelog.
- **FR-010**: Every Python function retained after cleanup MUST have a docstring stating purpose, each parameter, return value, and raised errors. Every exported web console function and component MUST have a documentation comment stating purpose, inputs, and output; module-private console helpers need only a self-explanatory name.
- **FR-010a**: Where a docstring is rendered to an operator — a CLI command's help text, an HTTP route handler's API description — the rendered prose MUST be preserved unchanged, and the parameter, return, and error documentation MUST be carried by the surrounding declarations (option help strings, response models, field descriptions) rather than added to the rendered text. A function documented this way satisfies FR-010 and is not an exception-register entry.
- **FR-011**: Cleanup of interface or abstract methods MUST be applied to every implementation in the same change.
- **FR-012**: Boolean behaviour-switch parameters MUST be replaced by two intent-named functions by default; where a split would duplicate a body of more than ten statements, an existing enumeration or option object MUST be used instead. No new enumeration or option type MAY be created for a flag that recurs in fewer than three signatures; when the same flag recurs in three or more signatures (FR-008's reuse threshold), one shared enumeration MAY replace it and MUST be recorded in the implementation plan's Complexity Tracking table.
- **FR-013**: Modules and folders whose names do not describe their responsibility MUST be renamed or moved to a descriptive location, with every import, string-referenced path, document reference, and orphan-guard entry updated in the same change and the move recorded in the structural changelog. Candidates are identified through the judgment-tag path: the inventory generator proposes one `module_name_review` per module, the review agent confirms or rejects it under FR-002b, and confirmed moves are executed in the owning package's cleanup increment. Such moves are cleanup work, not gap-register remediation; FR-026 does not apply to them.
- **FR-014**: Cleanup MUST be delivered as one increment per package (each top-level sub-package of the Python package, the package's root-level modules together as one increment, each service, and the web console), and the automated checks for the affected language MUST pass at the end of each increment before the next begins.
- **FR-014a**: An increment whose checks fail and cannot be made green within three fix-and-verify attempts MUST be reverted to the last green state rather than left red or carried forward. The function or module that caused the failure MUST then be either recorded in the exception register with its reason, or split into its own smaller increment, and the retried increment MUST pass before the next package begins.
- **FR-014b**: Functions added to the branch after the baseline inventory MUST be inventoried, tagged, and cleaned to the same target as the baseline set; the final regeneration is the measurement point for every inventory-based success criterion.

**Architecture assessment**

- **FR-015**: The assessment MUST run before any signature cleanup begins, so that every evidence pointer refers to the stabilised baseline commit (the tree produced by FR-027b) rather than to a partially cleaned tree. Baseline stabilisation is the only code change permitted before the assessment, and any gap it incidentally closes MUST still be recorded in the register with its resolution.
- **FR-016**: The assessment MUST cover every component: CLI, accelerator service, agent service, web console, migration engine, phase orchestration, pipeline transformation, state persistence (all backends and the job store), authentication and role enforcement, token management, audit writing, and every integration seam between them.
- **FR-016a**: The assessment MUST also cover deployment and continuous-integration artefacts — compose files, container images, and CI workflow definitions. Gaps found there MUST be rated high at most, under the same rule that excludes deployment topology from the critical criteria.
- **FR-017**: The assessment MUST evaluate each component against all six constitution principles and against these migration-safety properties: idempotency, resumability after interruption, scope-targeted rollback, validation after transfer, secret containment, and human approval before irreversible action.
- **FR-018**: Each gap MUST be recorded in a markdown gap register in the feature directory with identifier, component, violated principle or property, evidence, severity, blast radius, and status.
- **FR-019**: Severity MUST be assigned using the criteria in User Story 3, Scenarios 2 and 3: any gap meeting one critical test is critical; the single-point-of-failure test applies to in-code failure handling only, never to deployment topology.
- **FR-020**: The register MUST include a summary with counts per severity and the list of critical and high gaps.
- **FR-021**: A separate review agent MUST re-derive every critical and high rating from the recorded evidence and the constitution; every rating it cannot reproduce MUST be surfaced to the operator as a dispute before remediation of that gap begins.

**Remediation**

- **FR-022**: A gap rated **critical** MUST be remediated as soon as the review agent confirms its rating, without waiting for signature cleanup; cleanup of the affected code then proceeds on the remediated version. Remediation of **high** gaps MUST begin only after signature cleanup is complete. Every critical and high gap MUST be remediated within this feature, or recorded as deferred with the named blocker — an external dependency or infrastructure change, or, for the coverage shortfall only, the effort scoped out under FR-027a — and an in-scope compensating control (for the coverage shortfall, the never-lowered ratchet).
- **FR-023**: Every remediation MUST include an automated regression check that fails if the gap is reintroduced. The check MUST be proven once at authoring time by temporarily reverting the fix, observing the check fail, and restoring the fix; the register entry MUST record that this proof was performed.
- **FR-024**: Every remediation that would change a public contract MUST be listed in the implementation plan with its migration note for existing deployments; approval of the plan constitutes approval of those changes, and no such change MAY be applied before plan approval.
- **FR-025**: Remediation of safeguard-layer gaps MUST be applied at the shared choke point through which all affected callers route.
- **FR-026**: Medium and low gaps MUST remain in the register with a recommended follow-up and MUST NOT be remediated within this feature.

**Verification & documentation**

- **FR-027**: At completion, the full Python automated test suite, lint, and type checks MUST pass, and the web console's existing type-check, lint, and tests MUST pass. No new coverage threshold is introduced for the console.
- **FR-027a**: Coverage MUST be measured with no package excluded from measurement, and the enforced threshold MUST equal the honest figure measured once the baseline is stabilised, raised to the newly measured figure after every increment and never lowered. Reaching the constitutional 85% is NOT in scope for this feature: the shortfall MUST be recorded as a high gap in the register with a follow-up owner and the 85% target named as outstanding.
- **FR-027b**: Before the first cleanup increment, every test failing at the feature's starting commit MUST be fixed, or deleted where it exercises only code that earlier commits removed, so that the suite is green. Deletions MUST be recorded in the structural changelog, and the post-stabilisation collected count MUST be recorded as the baseline for SC-004.
- **FR-028**: The architecture document, the AI-assistant guidance file, the README, and every other document under the documentation directory MUST be updated so that every referenced module, function, and endpoint exists, and every remediated gap is described in its corrected form. Completed feature specifications (001–012) are historical records and MUST NOT be rewritten; a stale path in one of them is not a defect under this requirement.
- **FR-029**: The structural changelog MUST record every file move, rename, and deletion performed by this feature, as one entry per cleanup increment. Each entry MUST list moved, renamed, and deleted files individually, and MUST record deleted functions as a count together with a pointer to the inventory rows that identify each one — the git ref of the pre-increment inventory file plus the package's rows tagged `dead` at that ref (the generator never writes `disposition == "delete"` itself) — because regenerated inventories drop rows for functions that no longer exist.
- **FR-030**: The orphan-module guard allowlist MUST be updated for every dynamically imported module added, renamed, moved, or deleted.

### Key Entities

- **Function Inventory Entry**: one function; attributes: location, language, current signature, problem tags, reference count, disposition (clean / delete / exception). Stored machine-readably in the feature directory; regenerated by script.
- **Judgment-Tag Decision**: the review agent's confirmation or rejection of one proposed judgment tag on one function, or of one `module_name_review` proposal on one module (FR-013); attributes: function or module key, proposed tag, decision, rationale, whether it was escalated to the operator, the signature and docstring (or module path) state the decision was made against. Stored in a decisions file in the feature directory and reused by every regeneration until that state changes.
- **Protected Entry-Point List**: functions never auto-deleted regardless of reference count: CLI command handlers, HTTP route handlers, program and service entry points, dynamically registered tools and plugins, factory functions named in project documentation. Maintained alongside the inventory.
- **Exception Register Entry**: a function that cannot reach zero tags without behaviour change; attributes: location, unmet rule(s), reason, follow-up owner.
- **Architecture Gap**: a deviation from constitution or migration-safety property; attributes: identifier, component(s), violated principle/property, evidence, severity, blast radius, status (open / disputed / remediated / deferred), resolution, regression-check location.
- **Gap Register**: the ordered markdown collection of gaps with a severity summary, stored in the feature directory; the decision artefact for remediation.
- **Rating Dispute**: a critical or high rating the review agent could not reproduce; attributes: gap identifier, original rating, reviewer's proposed rating, reviewer's reasoning, operator decision.
- **Public Contract**: any externally observable interface that cleanup must preserve — CLI surface, HTTP surface, environment variables, persisted schemas, inter-service messages. The list is exhaustive; agent tool schemas and the package's importable Python API are excluded and may change.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of functions in the inventory have zero problem tags or an exception-register entry; the exception register contains no more than 2% of the total function count, or carries a recorded operator decision authorising the overrun. Zero judgment-tag proposals remain pending at the final regeneration.
- **SC-002**: 100% of externally observable contracts are unchanged, demonstrated by contract and integration tests passing without modification to their expectations. The comparison point is the stabilised baseline (FR-027b): tests deleted there because the code they covered was already gone are outside this measurement, and no expectation may change after the baseline is frozen except through an approved contract change (FR-024).
- **SC-003**: Zero new runtime dependencies, zero new runtime configuration keys (guard-tool configuration excluded, FR-008), and zero new abstraction layers introduced by signature cleanup.
- **SC-004**: The full Python suite passes with coverage measured without exclusions and at or above the ratchet value carried from the previous increment; the test count is at or above the post-stabilisation baseline minus the tests that exclusively exercised deleted functions; the web console's type-check, lint, and tests pass.
- **SC-005**: 100% of critical and high gaps are remediated or deferred with a compensating control; each remediated gap has a regression check whose failure against the unfixed code was observed and recorded at authoring time.
- **SC-006**: The review agent reproduces every critical and high severity rating from the recorded evidence, or every non-reproduced rating has a recorded operator decision; zero gaps are remediated with an open dispute.
- **SC-007**: 100% of module, function, and endpoint references in the architecture document, the assistant guidance, the README, and the documentation directory resolve to existing artefacts; completed specs 001–012 are excluded from this measurement.
- **SC-008**: An evaluating agent with no access to the repository, given only a function's signature and docstring, correctly states what it takes and returns for 95% of a 40-function random sample; each answer is scored against the function's body by the maintainer running the check.
- **SC-009**: Every file moved, renamed, or deleted by this feature appears individually in the structural changelog, and every deleted function is identifiable from the inventory rows the changelog entry points to.
- **SC-010**: Every per-package cleanup increment ends with the affected language's automated checks passing; zero increments are started while the previous one is red, and any increment that could not be made green was reverted rather than carried forward.

## Assumptions

- "Each part of the source code" means the Python package, both services, and the web console; all are inventoried, tagged, and cleaned. Test code is updated as a consequence of signature changes but is not itself subjected to the signature-quality tags. Generated files, vendored code, database migration scripts, and transformer mapping tables are excluded from the inventory and listed as such.
- Public contracts are frozen for this feature, and FR-006's list of them is exhaustive. Internal signatures — including agent tool schemas and the package's importable Python API — are free to change, with no compatibility aliases left behind. Where a gap can only be closed by changing a public contract, the change is batch-approved through the implementation plan (FR-024).
- The constitution's six principles plus the listed migration-safety properties are the sole yardstick for "gap"; industry best practice is applied through those, not as a separate open-ended checklist.
- "Critical" is bounded by the five criteria in User Story 3, Scenario 2, with the single-point-of-failure criterion limited to in-code failure handling. "High" is bounded by Scenario 3. Remediation scope is critical + high; medium and low are out of remediation scope.
- The existing specification set (001–012) documents intended behaviour; where the code deviates from a completed spec, that is evidence for a gap, and where a spec is silent, the constitution decides.
- The signature rules applied are: descriptive verb-noun names; all parameters and returns typed; five parameters or fewer excluding the receiver; no boolean behaviour-switch parameters; no mutable defaults; no unused parameters; a docstring per Python function and a documentation comment per exported console function or component. These are the recognised clean-code rules and are not expected to need negotiation.
- The lazy-senior-developer discipline (delete over add, reuse over reinvent, smallest correct diff, no speculative structure) governs how cleanup is done and is enforced by FR-008, FR-012, and SC-003.
- The work lands on the existing `feature/ado-agentic-ai` branch; no new git branch is created by this specification.
- The web console's existing type-check, lint, and test tooling is its pass gate; no console coverage threshold is introduced.
- The suite is red at the starting commit (measured 2026-09-07: 50 failed, 16 errors, 790 passed) from in-flight work on the branch, and honest coverage is 56–60% against a gate that asserts 85%. Both are pre-existing conditions, not consequences of this feature; FR-027b stabilises the first before any increment, and FR-027a converts the second into a ratchet plus a registered gap.
- The order of work is fixed: baseline stabilisation → assessment → per-package cleanup → high-gap remediation → documentation, with one exception: confirmed critical gaps are remediated immediately after the review agent's pass, ahead of or alongside cleanup (FR-022). The review agent's pass on the register happens between assessment and cleanup so that disputes are settled before any code moves.
