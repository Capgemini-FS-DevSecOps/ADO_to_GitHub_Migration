## Threats by Category

### LLM01: Prompt Injection

- **THR-01-001**: `ado2gh/agents/migration_agent/nodes/intent.py` — NEW. `_build_session_context` interpolates ADO-sourced repository names into a markdown block (`intent.py:78-84`) that `nodes/orchestrator.py:438` concatenates onto the role prompt and `:446` sends as a `SystemMessage`. The names are neither delimited, escaped nor length-capped per item, so text controlled by anyone able to create a repository in the scanned ADO organisation lands in the highest-trust channel — the same channel that carries the CA-001 dry-run rule and the plan-approval rules. Same construction at `nodes/orchestrator.py:532` and `:674`.
  Likelihood: **Med** | Impact: **High** | Risk: **High**
  - Mitigation: Move discovery-derived values out of the system message into a separate user-role block with an explicit untrusted-data delimiter, and reject or neutralise repo names containing newlines, markdown headings or role markers at the point they enter `session["discovery_snapshot"]`. `hitl/intake_llm.py:106-113` already does the right thing — it wraps operator text and repo names in a JSON envelope with distinct `user_message` / `session_context` keys — and is the pattern to copy.

- **THR-01-002**: `ado2gh/agents/migration_agent/tools/validator_tools.py` — NEW. `fetch_github_workflow` base64-decodes repository file content at `validator_tools.py:168` and returns it as a tool result; `nodes/validator_investigation.py:722-736` then `json.dumps` the whole tool-result batch into a bare `HumanMessage` bounded only by a `[:12000]` truncation. Arbitrary attacker-authored file content in a source or target repository therefore reaches the validator's context as instruction-adjacent text, and the validator is the agent whose verdict gates the operator's view of whether a migration succeeded.
  Likelihood: **Med** | Impact: **High** | Risk: **High**
  - Mitigation: Fence fetched file content in an explicitly labelled untrusted block, cap per-file size before it enters the batch, and instruct the validator prompt that file content is evidence to be reported on, never instructions to follow. Re-derive the pass/fail verdict from the deterministic baseline checks rather than from free-text model reasoning over file bodies.

- **THR-01-003**: `services/agent/routes/session_routes.py` — partially registered (**GAP-019**, open, high, for the authorization half; the transcript-injection half is NEW). `provision_session` (`session_routes.py:253-263`) takes no `Request`, performs no permission or ownership check, and at `:262` appends `{"role": req.actor, "content": f"provision:{req.tier}"}` directly onto `session["messages"]`. Both `actor` and `tier` are unconstrained client strings (`services/agent/routes/_helpers.py:98-103`), so an unauthenticated caller who knows a session id can insert a message with an arbitrary role label and arbitrary body into the transcript the model reads back. GAP-019 records the `actor != "approver"` self-certification but rates the write's blast radius as "an unauthenticated write to inert session state"; line 262 is not inert.
  Likelihood: **Med** | Impact: **High** | Risk: **High**
  - Mitigation: Give the route a `Request`, derive the actor from `request.state.platform_user` via `attach_actor_to_session`, and route the message through the masking entry point rather than appending to the list directly. Constrain `tier` to an enum. Worth folding into GAP-019's resolution so one change closes both halves.

- **THR-01-004**: `ado2gh/agents/migration_agent/nodes/planner.py`, `nodes/planner_research.py`, `nodes/validator_investigation.py` — NEW. Untrusted ADO and GitHub payloads are embedded into planner and validator prompts with JSON encoding but no trust boundary: discovery rows at `planner.py:526`, probe findings at `:527`, prior plan at `:546`, all joined into one `HumanMessage` at `:555`; raw tool argument/result batches at `planner_research.py:479-488`; executor log, executor metadata and plan summary at `validator_investigation.py:386-417` into the single `HumanMessage` at `:620`. JSON encoding prevents structural breakout but not semantic injection, and nothing tells the model these regions are data.
  Likelihood: **Med** | Impact: **Med** | Risk: **Medium**
  - Mitigation: Introduce one shared helper that wraps externally sourced payloads in a labelled untrusted-data envelope and use it at all six sites, so the boundary is stated once rather than re-decided per call site.

- **THR-01-005**: skill corpus (`.claude/skills/`, `.agents/skills/`) — NEW. All 31 `SKILL.md` files interpolate the unescaped `$ARGUMENTS` value into the instruction stream, both in a trailing context section and mid-body (for example `.claude/skills/speckit-clarify/SKILL.md:241`, `.claude/skills/speckit-tasks/SKILL.md:134`, `.claude/skills/speckit-checklist/SKILL.md:128`). Verified by search that no skill passes `$ARGUMENTS` into a shell command, script invocation or file path, so the pattern steers agent behaviour only — it does not reach a shell. Raised above "dismissed" because `speckit-conduct-run` composes and forwards arguments to sub-agents, so the value is not always typed by the human at the keyboard.
  Likelihood: **Med** | Impact: **Low** | Risk: **Low**
  - Mitigation: Keep the value out of shell commands (already the case, and worth an explicit rule so it stays true), and have skills that forward composed arguments to sub-agents quote them as data rather than splice them into instruction prose.

### LLM02: Sensitive Information Disclosure

- **THR-02-001**: `ado2gh/agents/migration_agent/nodes/planner_research.py` — NEW. CA-003 masking is applied at the operator-facing boundary only. The same tool results that `utils.py:292` passes through `redact_payload` before streaming, and that `utils.py:91` masks before storing in the chat transcript, are written raw into the model conversation at `planner_research.py:479-488` — `json.dumps({"tool_results": batch_results, ...})` with no redaction — and that conversation is persisted by the `AsyncSqliteSaver` built at `graph/builder.py:140-148`. A credential returned by any accelerator or GitHub response therefore lands unmasked in the checkpoint database while the operator's own view of the same data is masked.
  Likelihood: **Med** | Impact: **High** | Risk: **High**
  - Mitigation: Apply `redact_payload` to `batch_results` before the `json.dumps`, and to the equivalent batch at `nodes/validator_investigation.py:722-736`. Treat the model context and the checkpoint as CA-003 sinks on the same footing as the SSE stream and the chat feed.

- **THR-02-002**: `services/agent/routes/_helpers.py` — residual of **GAP-011** (recorded remediated). `ado2gh/agents/migration_agent/utils.py:70-99` documents itself as the "sole entry point for the in-memory message list, so this is where CA-003 masking is applied". It is not sole: `_helpers.py:397-417` `_add_message` is a full parallel writer that appends `content` verbatim with no `mask_secrets`, and it has more than a dozen call sites across `execution_routes.py`, `form_routes.py`, `message_routes.py` and `session_routes.py`. Client-controlled text reaches it unmasked at `form_routes.py:140` and `:403` (a summary rendered from the raw `values` dict, which `_helpers.py:86-89` accepts as unconstrained `dict[str, Any]`) and at `execution_routes.py:322` (a `reason` taken from a raw request dict). `session_routes.py:262` is a third writer that bypasses even `_add_message`.
  Likelihood: **Med** | Impact: **High** | Risk: **High**
  - Mitigation: Make `_add_message` delegate to the masking entry point instead of building its own dict, and remove the direct `session["messages"].append` at `session_routes.py:262`. A test that asserts the message list has exactly one writer would keep the docstring's claim true.

- **THR-02-003**: `ado2gh/agents/migration_agent/tools/executor_tools.py`, `tools/planner_tools.py`, `tools/validator_tools.py` — NEW. Every tool wraps its call in `except Exception as e: return {"error": str(e)}` (`executor_tools.py:101,111,138`; `planner_tools.py:59-60,69-70,81-82`; `validator_tools.py:71-72,79-80,119-120,147-148,176-177`). httpx exception strings carry the full request URL, and the resulting dict is both persisted and fed back into the LLM prompt, so a request whose URL or headers carried a credential re-enters the context as an error string. `ado2gh/logging_config.py:91` masks the log path (GAP-064) but this is a different sink. Same shape at `services/agent/routes/message_routes.py:163-164`, `form_routes.py:168` and `:454`, which return the raw exception to the HTTP client.
  Likelihood: **Med** | Impact: **Med** | Risk: **Medium**
  - Mitigation: Return the exception type and a stable code rather than `str(e)`, or route the string through `mask_secrets` before it becomes a tool result. `ado2gh/api/live_approval_store.py:326` already does the type-not-message thing and is the precedent.

- **THR-02-004**: `services/agent/routes/run_routes.py` — NEW. `/health` is auth-exempt (`services/agent/main.py:85-88`) yet returns the configured `ACCEL_URL` and the raw connection-error string at `run_routes.py:63` and `:80`, disclosing internal topology to an unauthenticated caller.
  Likelihood: **Med** | Impact: **Low** | Risk: **Low**
  - Mitigation: Report reachability as a boolean plus a status code; keep the target URL and the error text in the server log.

### LLM03: Supply Chain

- **THR-03-001**: `.specify/extensions.yml` and the skill corpus — NEW. The hook registry is tracked in git (confirmed via `git ls-files`), while the skill bodies are not. Every skill's Pre-Execution Check protocol reads that file and, for a hook with `optional: false`, is instructed to emit `EXECUTE_COMMAND` and run it with no operator confirmation; the repository currently registers one such mandatory hook (`before_plan` → `speckit.red-team.gate`). A commit to the tracked registry therefore causes every future skill run in every clone to auto-invoke a named command. Blast radius is bounded to commands the agent already has installed — the field names a slash command, not a shell string — and the hook graph was checked for cycles and has none.
  Likelihood: **Low** | Impact: **Med** | Risk: **Low**
  - Mitigation: Treat `.specify/extensions.yml` as a security-relevant file in review, and have the mandatory-hook branch name the command it is about to run and require acknowledgement on first use in a workspace rather than on every run.

### LLM04: Data and Model Poisoning

- **THR-04-001**: `ado2gh/agents/migration_agent/nodes/planner_research.py` — NEW. `planner_research.py:458-463` writes an accelerator response straight into durable session state — `session["discovery_snapshot"] = result_content` — and selects it on nothing more than the LLM-chosen endpoint string containing the substring `/discovery` (`:460`). That snapshot is persisted with the session and is later rendered into the **system prompt** by `nodes/intent.py:70-84`. Model-chosen data therefore becomes durable state that steers every later turn, and the substring test is satisfied by any path ending in `/discovery`, including one reached through the traversal described in THR-05-001.
  Likelihood: **Med** | Impact: **Med** | Risk: **Medium**
  - Mitigation: Accept a discovery snapshot only from a server-constructed endpoint whose profile id the server chose, validate the payload against a schema before storing it, and drop the substring match in favour of an exact path comparison.

### LLM05: Improper Output Handling

- **THR-05-001**: `ado2gh/agents/migration_agent/tools/executor_tools.py`, `nodes/orchestrator_tools.py`, `tools/planner_tools.py`, `tools/validator_tools.py` — NEW *(measured)*. LLM-supplied endpoint strings are concatenated after a fixed prefix with only `lstrip("/")` applied: `executor_tools.py:109` builds `/v1/ado/{endpoint}`, `:136` builds `/v1/github/{endpoint}`, and `nodes/orchestrator_tools.py:116,123` repeat both in the inline dispatcher. Measured against the installed httpx 0.28.1: `Client(base_url=...)._merge_url("/v1/ado/../../v1/migrate/git-mirror")` resolves to `http://accelerator:8080/v1/migrate/git-mirror`, so dot-segments in a model-chosen endpoint escape both prefixes. Two consequences. `ado_api_query` is declared read-only and is excluded from guardrail wrapping by the `read_only` set at `executor_tools.py:195`, yet can reach any accelerator GET route. And for `github_api`, the guardrail validates a `repository_id` against the approved plan while the request it authorises no longer targets that repository — the scope check and the request have been decoupled.
  Likelihood: **Med** | Impact: **High** | Risk: **High**
  - Mitigation: Normalise and re-check the path after joining, rejecting any result that does not still start with the intended prefix; or percent-encode each path segment and refuse segments equal to `..`. Do it in one shared helper, since six call sites repeat the construction. Pair it with a server-side allowlist of reachable accelerator routes per tool, so the read-only tool is read-only by construction rather than by prefix convention.

- **THR-05-002**: `ado2gh/agents/migration_agent/tools/validator_tools.py` — NEW. LLM-supplied values are spliced into query strings with no encoding: `validator_tools.py:130-131` builds `...workflows?ref={ref}` and `:161-162` does the same for `workflow_path`. `:86-87` encodes spaces only. A value containing `&` or `#` injects or truncates query parameters on the upstream GitHub request.
  Likelihood: **Med** | Impact: **Med** | Risk: **Medium**
  - Mitigation: Build these with `urllib.parse.quote` per segment and `urlencode` for the query, rather than f-strings.

### LLM06: Excessive Agency

- **THR-06-001**: `ado2gh/agents/migration_agent/guardrails.py` — NEW *(measured)*. The approved-plan scope check is conditional on the plan's repo set being non-empty: `guardrails.py:263` derives `plan_repos` from `migration_plan.get("repos", [])` and `:264` guards the whole target-resource check behind `if plan_repos:`, so an empty set falls through to the terminal `ALLOW` at `:286`. Measured by calling `evaluate_guardrail` directly — an operator-approved plan with no `repos` key returns `allow` "Plan authorized and resource validated" for `call_accelerator` POST to `/v1/migrate/secret-provision`, and a plan that spells the key `repositories` returns `allow` for a `github_api` PUT whose `repository_id` is not in the plan at all. The plan shape is produced by the planner model, so a key-name drift in model output silently disarms the scope check for every subsequent write. Compounding this, `CallAcceleratorArgs` (`tools/orchestrator_tools.py:74-103`) declares neither `target_resource` nor `repository_id`, the only two keys `guardrails.py:162-166` reads, so a well-formed plan makes every `call_accelerator` POST unsatisfiable at `:265` — the guard is simultaneously too strict on the correct path and open on the degenerate one, which pressures operators toward whichever plan shape happens to work.
  Likelihood: **Med** | Impact: **Critical** | Risk: **High**
  - Mitigation: Fail closed on an empty or unrecognised repo set — a write with nothing to check against is unauthorised, not authorised. Validate the plan against a schema at approval time so a plan missing `repos` can never reach `plan_approved=True`. Add `repository_id` to `CallAcceleratorArgs` so the accelerator write path can satisfy the scope check it is subject to.

- **THR-06-002**: `ado2gh/agents/migration_agent/guardrails.py` — NEW *(measured)*. The evaluation ends in a default-allow branch: `guardrails.py:307-315` returns `ALLOW` with reason "Unknown operation — allowed by default" for any tool name present in none of `_READ_OPERATIONS`, `_WRITE_OPERATIONS` or `_DELETION_OPERATIONS` (`:91-107`). Measured: `evaluate_guardrail(agent_role="executor", tool_name="provision_secret", ...)` returns `allow`. An allowlist whose fall-through is "permit" means every tool added later is unguarded until someone remembers to list it, and the three sets already omit `invoke_planner`, `invoke_bulk_planner` and `generate_plan`-adjacent names.
  Likelihood: **Med** | Impact: **High** | Risk: **High**
  - Mitigation: Invert the default to BLOCK with a reason naming the unregistered tool, and add a test that fails when a tool exposed by any `get_*_tools` builder is absent from the classification sets.

- **THR-06-003**: `ado2gh/agents/migration_agent/nodes/orchestrator.py` — NEW. The CA-002 confirmation for rollback is decorative. `orchestrator.py:363-375` appends a `confirm_rollback` checkbox with `"required": True` to the cancellation form, but the handler at `:310-317` dispatches on `values.get("action") == "rollback"` alone and never reads `confirm_rollback`; `_execute_rollback` then deletes the GitHub resources created by the session. `hitl/forms.py:37` copies `required` through as a client-side hint and nothing enforces it server-side, and `hitl/schemas.py:161-170` `FormIntakeSubmission` has no such field, so a form submission posted directly to the form-submit route performs an irreversible deletion with no confirmation of any kind.
  Likelihood: **Med** | Impact: **Critical** | Risk: **High**
  - Mitigation: Require `values.get("confirm_rollback") is True` in the handler before calling `_execute_rollback`, and enforce `required` fields server-side in `prepare_form_submission` so the next destructive form does not repeat this.

- **THR-06-004**: `services/agent/routes/execution_routes.py` — residual of **GAP-002** (recorded remediated). `approve_session` sets `session["dry_run"] = False` directly at `execution_routes.py:160` when the session carries no `live_approval_id`, recording `approval.approved = True` without any platform approval row. Its only gate is `_require_approve_live(request)` at `:122`, and that helper is a complete no-op when `auth_enabled()` is false (`services/agent/routes/_helpers.py:237-244`) — the configuration CLAUDE.md documents as the default (`ADO2GH_AUTH_ENABLED=false`). GAP-002's fix removed the `auth_enabled()` dependency from the policy functions in `policies.py`, but this route bypasses the policy layer entirely and writes the flag itself, which directly disarms the per-tool CA-001 blocks at `guardrails.py:198` and `:220`. Not rated higher because a compensating check survives: `_helpers.py:576` re-evaluates `session_requires_live_approval` before starting a PEV run and enqueues an approval instead, and `session_routes.py:93` does the same.
  Likelihood: **Med** | Impact: **High** | Risk: **High**
  - Mitigation: Route this branch through `policies.enforce_live_mode_request(request, ExecutionMode.LIVE, session=session)` as `confirm_live_execution` already does at `:185`, rather than assigning the flag. Separately, `_require_operate` and `_require_approve_live` should fail closed rather than return when auth is disabled, or the disabled-auth deployment should be documented as trusted-network-only.

- **THR-06-005**: `ado2gh/agents/migration_agent/guardrails.py` — NEW *(measured)*. The CA-001 dry-run blocks are written `if session and session.get("dry_run") is not False:` (`guardrails.py:198`, `:220`). The `is not False` half is correct and is the GAP-076 fix, but the leading `if session and` makes a falsy session skip the check entirely — and `wrap_tool_with_guardrail` supplies `{}` when no `session_getter` is configured (`:348`). Measured: with `session=None`, a `github_api` POST is allowed. The remaining plan-approval check limits the damage, which is why this is not rated with THR-06-001.
  Likelihood: **Low** | Impact: **High** | Risk: **Medium**
  - Mitigation: Drop the `session and` conjunct so a missing session is treated as dry-run, which is the fail-safe reading and what CA-001 requires.

- **THR-06-006**: `ado2gh/agents/migration_agent/nodes/orchestrator_tools.py` — residual of **GAP-076** (recorded remediated). `orchestrator_tools.py:242` computes `dry_run = session.get("dry_run", args.get("dry_run", True))` and `:245` assigns it back to the session. When the session has no `dry_run` key, the value comes from the orchestrator model's tool arguments and becomes the session's execution mode with no call to `enforce_live_mode_request`. The value is also written without `coerce_dry_run`, the single-reader helper GAP-076 introduced at `utils.py:23` — its remediation lists `guardrails.py:198`/`:220`, `session/store.py:46`/`:275`, `session/lifecycle.py:183`, `planner_plan_builders.py:182` and `executor/plan.py:241`, but not this site — so a present-but-null session value is written straight through.
  Likelihood: **Low** | Impact: **Critical** | Risk: **Medium**
  - Mitigation: Read the flag through `coerce_dry_run` here too, and never let a model-supplied `dry_run` seed the session; default to dry-run and require the operator's explicit mode selection.

- **THR-06-007**: `ado2gh/agents/migration_agent/tools/executor_tools.py` — NEW, related to registered **GAP-078** and **GAP-018** (both open, unsafe LIVE defaults). `call_accelerator` defaults its HTTP method to the mutating verb in both the implementation (`executor_tools.py:84`, `method: str = "POST"`) and the schema the model sees (`tools/orchestrator_tools.py:77-80`), so a tool call that simply omits `method` performs a write against a `/v1/migrate/*` endpoint. The sibling `github_api` defaults to `GET` (`executor_tools.py:115`), which is the correct polarity. The guardrail still evaluates the resulting POST, which is why impact is Medium rather than High.
  Likelihood: **Med** | Impact: **Med** | Risk: **Medium**
  - Mitigation: Default `method` to `GET` in both the function and the args schema, and require the model to name a mutating verb explicitly — the same safe-default reasoning the operator decision behind GAP-018/068/078 is already weighing.

- **THR-06-008**: `ado2gh/agents/migration_agent/tools/orchestrator_tools.py`, `tools/planner_tools.py`, `tools/validator_tools.py`, `nodes/orchestrator_tools.py` — NEW. `wrap_tool_with_guardrail` has exactly one call site, `tools/executor_tools.py:205`. The orchestrator, planner and validator tool builders never wrap their tools, and the inline dispatcher at `nodes/orchestrator_tools.py:87-329` dispatches on the tool-name string and never calls `evaluate_guardrail` at all — while writing session state that later gates execution (`generate_plan` writes `session["migration_plan"]` at `:127-155`; `invoke_planner` writes `session["plan_repository_id"]` and `session["dry_run"]` at `:244-249`). Present exposure is limited because those tools' bodies are read-only today; the finding is that the guardrail is one call site rather than a platform-wide interceptor, so it protects by placement rather than by construction.
  Likelihood: **Low** | Impact: **Med** | Risk: **Low**
  - Mitigation: Wrap at the point tools are bound to the LLM rather than per builder, so a new tool is guarded by default; or assert in a test that every tool returned by any `get_*_tools` builder carries the wrapper.

### LLM07: System Prompt Leakage

- **THR-07-001**: systemic — skill corpus and `ado2gh/agents/migration_agent/prompts/` — NEW. All 31 `SKILL.md` files and the four agent role prompts are plain readable workspace files, so any party who can read the checkout, or who can induce a file read through the agent, learns the exact operating instructions. This is inherent to file-based skills and prompts and is reported once rather than per file. It is raised above informational because `prompts/executor.md` restates the guardrail rules in operational detail — which methods are read-only, which require an approved plan, which require confirmation — so the disclosure names the precise conditions the findings above turn on.
  Likelihood: **High** | Impact: **Low** | Risk: **Medium**
  - Mitigation: Accept the disclosure — file-based prompts are the design — but stop treating prompt text as a control. Every rule stated in `prompts/executor.md` must also be enforced in `guardrails.py`, since an adversary reading the prompt knows exactly which of them are advisory.

### LLM09: Misinformation

- **THR-09-001**: `ado2gh/agents/migration_agent/hitl/form_fields.py` — registered, **GAP-024** (open, high). `form_fields.py:204` sets the `confirm_execute` recommendation to the boolean `False` — the safe value, meaning do not start execution on confirm — and `:100` stringifies every recommendation with `str(recommended_value).strip()[:120]`, producing `"False"`, which is truthy in the browser. `:145` has the same shape for the `dry_run` field, where the string `"false"` means live. The operator is therefore shown a confirmation control pre-set to the unsafe answer, and a confirmation whose default is "yes" is not a confirmation.
  Likelihood: **Med** | Impact: **High** | Risk: **High**

### LLM10: Unbounded Consumption

- **THR-10-001**: `services/agent/routes/_helpers.py`, `services/agent/routes/message_routes.py`, `services/agent/routes/form_routes.py` — NEW. Session and run state is retained without bound: `_helpers.py:48-49` holds `_runs` and `_sessions` as process-global dicts with no TTL and no eviction, removed only by an explicit `DELETE /v1/sessions/{id}`.   Likelihood: **Med** | Impact: **Med** | Risk: **Medium**
  - Mitigation: Give sessions a TTL with a sweep, cap concurrent sessions and concurrent streams per actor, and bound each stream by wall-clock duration and total bytes.

- **THR-10-002**: `services/agent/routes/_helpers.py`, `ado2gh/agents/migration_agent/tools/orchestrator_tools.py` — NEW. No request model in `_helpers.py` declares a single `max_length`, `pattern` or numeric bound. `_helpers.py:83` accepts `message: str = ""` unconstrained and `:89` accepts `values: dict[str, Any]` unconstrained, both of which reach the LLM; `tools/orchestrator_tools.py:125-130` accepts `repository_ids: list[str]` with no `max_length`, and `_helpers.py:512-519` then builds a work item per matching repository with no ceiling.   Likelihood: **Med** | Impact: **Med** | Risk: **Medium**
  - Mitigation: Add `max_length` to the free-text fields, a size and key-count bound to `values`, and a `max_length` to `repository_ids` matched to the documented batch ceiling.

- **THR-10-003**: `services/agent/routes/session_routes.py` — NEW.   Likelihood: **Med** | Impact: **Low** | Risk: **Low**
